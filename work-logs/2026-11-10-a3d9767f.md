### Static spark (`spark.js`, new; loaded on the home page and the Tinkering page)
- A full-window canvas (`position: fixed`, `pointer-events: none`, `z-index: 9999`, `aria-hidden`) draws the bolts; it only animates while a bolt is alive.
- **Geometry:** `nearest()` finds the closest point on a button's rounded rectangle (using its computed corner radius) and the gap to it (0 inside). The bolt is a midpoint-displacement path generated in bolt-relative units (u along, v sideways as a fraction of length), so each frame it is mapped onto live endpoints: the far end follows the cursor and the near end slides to the closest edge point. It re-strikes in a new random shape every 45ms. Drawn as a blue glow stroke plus a white core with hot spots at both ends; alpha fades over the bolt's life.
- **Firing rules (final):** a bolt fires when the cursor is outside a button and within the jump distance (50px). No new bolts while the cursor is over the button. The first move after leaving the button fires at once (allowed up to 2× the jump distance, for fast exits), replacing that button's previous bolt. Hovering just outside, a new bolt follows as soon as the last one ends (cooldown 0). Bolt life 200ms. Mouse only; off for touch and for reduced motion.
- **Iteration history:** started with one charge per approach and a 70px retreat distance to re-arm (felt broken: the user had to travel far before another spark); jump 26 → 50px, life 170 → 420 → 200ms; switched to time-based recharge (300 → 100ms after leaving, 300 → 100 → 0ms cooldown after a bolt); removed a "fast entry" rule that struck from the last outside position when the cursor jumped straight onto a button (it fired bolts while inside); finally made leaving strike immediately instead of after a wait, because a normal exit carries the cursor past 50px within 100ms.
- **Flash:** the button gets `.is-zapped` briefly (`button-zap` for `.button`, a filter-only `chip-zap` for nav chips so their own shadows aren't overridden).
- **Settings now come from `buttons.js`** (`Buttons.cfg`, read fresh on every move/frame) with built-in fallbacks: on/off, jump distance, duration, flicker interval, jaggedness, core and glow width, glow blur, core and glow colours, flash. It targets `.button, .nav .chip`.
- **Note:** the user's active button version ("Dark Wash and Rust") sets `spark: false`, so the spark is currently **off on the live site**. Turn it on in the Button Lab (Spark → Spark on) and save.

## Challenges and how we solved them

- **Restart button "stopped working"** (reported mid-session). Could not reproduce: headless Chrome at 1280 and 390px showed it on top and replaying the board. Asked the user for specifics (what happened, browser, real phone or responsive mode, hard refresh); no follow-up came.
- **Black halftone transitions in light mode.** Chrome reports `color-mix()` colours as `color(srgb …)` in 0–1, which `rgb()` parsed as near-black. Fixed in `rgb()`.
- **Headless Chrome won't go below ~500px wide.** Used a 390px iframe at first, then built a small CDP driver (`node` + WebSocket, `Emulation.setDeviceMetricsOverride`) in the scratchpad for phone-width screenshots and in-page measurements.
- **Off-centre tiles.** Tile pixel size came from `clientWidth` (rounded; real cell 61.656px), so tiles were drawn ~0.3% small and stretched; cells sat at different sub-pixel offsets. A first pass still left cells 122.125 device px wide because `aspect-ratio` recomputed width from height; fixed by giving `.sf` an explicit width too.
- **"Always above the dots."** The hard limit (374.5px) put "Recent Work" ~260px above the dots most of the time. A CPU simulation of the mask (480 frames over 4 minutes) found a real peak of 308px at 1600px wide (median 224), and 306px at 390px (95% under 240, median 187). That led to `peak()` at 80% noise for desktop and 75% of the peak on phones.
- **Lab save test touched the real versions file.** Backed up `split-flap-versions.js` first, saved and activated a "Light test" version through the UI, verified `activeLight`, then restored the file. The first save attempt saved nothing because the panel already matched the light active board; a `requestSubmit` save worked.
- **Dev server needed a restart** for the lab-server change; it was not running at first, then stopped and restarted without `--open`.
- **Light-mode screenshot capture landed partway down the page** on phone; retook as a plain viewport shot. Blackbird/Mazlan section screenshots had the same scroll problem (smooth scroll, lazy images); fixed with instant scrolling.
- **Colours-only light board made shadows too deep**, so the first lab fix was reverted and redone as a lab-only change (see above).
- **Project copy of grill-me could not be deleted** (permission check); left for the user.
- **Case study research limits:** most of the Mazlan Builder folder and part of the Mazlan folder are cloud-only on this Mac, so only the prototype's local files were read; the Mazlan event-feedback PDF is scanned images and unreadable. The Read tool can't render PDFs here, so Swift PDFKit scripts were used.
- **Spark tests rendered black screenshots.** The capture copied the last `<canvas>` on the page, which was another canvas; selected the spark canvas by its `z-index` instead.
- **New files 404'd on the dev server.** `tools/lab-server.mjs` only serves what `.vercelignore` allowlists and reads that file at startup; added the files to the allowlist and restarted the server (also needed for the new save route).
- **Sparks felt broken after leaving a button.** Distance-based and then 100ms time-based re-arming both failed in practice because a normal exit moves the cursor past the jump distance before the button re-arms; firing on the first move outside fixed it.
- **Label in front of overlays.** Absolutely positioned `::before`/`::after` painted over the label text; fixed with `isolation: isolate` on the chip and `z-index: -1` on the pseudo-elements.
- **Specificity with the lab.** The Halftone Lab's own `.chip` class would have clashed with the nav chips; the Button Lab uses `btn` for its panel buttons and the site rules are scoped to `.nav .chip`.
- **Shadow card titles wrapped** in the Button Lab ("Shadow 1" on two lines); kept on one line in CSS.

## Lessons learned

- The user iterates visually and fast: make the change, screenshot, give a short honest read, offer one or two alternatives, and don't wait for approval on small style tries.
- Measure before fixing layout bugs; the CDP driver plus `getBoundingClientRect` at multiple widths settled the tile question quickly.
- Inline custom properties set by `split-flap.js` (gap, frame pad) can't be overridden by CSS variables; override the real properties (`padding`, `gap`) instead.
- Theoretical bounds on noise-driven motion are far above reality; simulate.
- Don't push without being asked: Claude left 2c97fa1 unpushed until the user said "Ship here". "Ship it" means commit, update the log, and push.
- When a lab save goes wrong, the user wants a clean revert to the last shipped state first, then a narrower fix.
- For interaction feel (spark timing), the user tunes by numbers in quick succession; change exactly the named value and say what else it affects. When the user says "it is not working", find why the behaviour misses their intent rather than tweaking the number again.
- Visual direction can swing widely (knurled metal → black metal → grained steel → flat gradient); keep each try cheap and the structure reusable (custom properties, a renamed class) so the next swing is quick.
- Lab-tunable settings work best as CSS custom properties applied from a small shipped script, with matching defaults in the stylesheet.
- The user changes their mind on behaviour after seeing it (ending: spin-to-reveal, then shrug plus restart together); keep such changes small and reversible.
