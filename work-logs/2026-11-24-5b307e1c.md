**Weight:**
- Measured five encodings on four kinds of clip with SSIM against a near-lossless reference, then compared zoomed text frames.
- Now 24fps (was 30), H.264 `-crf 30 -preset veryslow -tune animation`. Total went from 6.1MB to 3.9MB.
- Each clip also has an AV1 copy (`NN.av1.mp4`, SVT-AV1 `-crf 60 -preset 4 tune=0`): 2.5MB total at the same SSIM.
- `drift-wall.js` uses AV1 only when `mediaCapabilities.decodingInfo` reports supported, smooth and power-efficient decoding; otherwise H.264.
- Posters are 0.8MB. A visitor fetches only clips in view: about 1.3MB per wall (H.264) or 0.9MB (AV1).
- 576-wide frames would save about another 20% but soften text. Offered, not done.
- `record.mjs` writes both encodes; `ENCODE_ONLY=1` re-encodes from raw recordings.

**Verified:** in headless real Chrome, the H.264 path and a forced AV1 path each played all 17 visible Groom Lake tiles with no errors. Headless Chrome on this M2 Pro reports AV1 as not power-efficient, so it uses H.264. After merging, the live site played 17 Groom Lake and 12 Mazlan tiles with no errors.

### Tagline ink-in fix for Safari (11-26, PR #57)

- Brian: on a phone the tagline "starts, then quickly freezes, then the whole text block appears fully formed."
- Cause: WebKit doesn't repaint an HTML element when the attributes of the SVG filter it wears (`filter: url(#…)`) change, only when it points at a different filter. It was reproduced in simulator Safari with a minimal page.
- Fix in `work.html`: `inkIn()` (record titles) and `goo()` (project sheet tagline) give each line two filters and swap between them each frame. `inkIn()`'s clock now advances at most 50ms per frame, so dropped frames slow the ink-in rather than skipping it. WebKit renders these filters on the CPU.
- Checked in simulator Safari (the Groom Lake title now goos through) and in headless WebKit (no errors). Not checked on a real iPhone.

## Lessons learned

- The user's names: "project name" is the small mono name, "tagline" the large title, "attr tags" the mono tag list, "info cards" the fields.
- Groom Lake's "intro montage" / "hero montage" is the film at the top of the project sheet, not the drift wall.
- The user doesn't want scroll speed or the pointer moving ambient pieces. Entrances should be tight and in reading order.
- When two scripts animate one block, give them one clock.
- Menu rules: header aligned and proportional to rows; seams and lamps; never scroll; no magnetic surface on rows.
- No hard or solid edge in shading under a docked element.
- Board: leaving content fades before the frame shrinks; hover lights only what the pointer is on; highlights fade; hit areas span a row's gaps.
- The painted metal text was rejected; a one-time glint was what the user chose to try.
- Changing Matte changes every menu that uses it. Say so when shipping.
- Moving screens: no cursor, every screen moves, loops lean toward 12s, light and dark mixed. The user notices choppiness and badly fitted device frames.
- For recorded app motion (scrolls, pushes, sheets), keep the capture's 60fps through every stage. Don't reduce frame rate in masters or encodes.
- Prototype and app source are the user's: drive them, never edit them.
- For interface video, AV1 at the same SSIM was about 40–65% of H.264's size here; use it only with hardware decoding when many play at once.
- A UI-test driver can record the iOS simulator without Accessibility permission or taking the mouse.
- Don't run encodes while the simulator is recording; extra CPU load can make captures stutter.
- Don't edit a clip list while a batch is reading it. In shell loops, keep the recorder from consuming the loop's stdin.
- When shipping from a branch made from main, say which uncommitted changes are **not** going out.
- Paper holds a fuller set of Blackbird screens (about 75, with dark mode) than the reel's assets. Paper exports go to `~/Downloads`.
